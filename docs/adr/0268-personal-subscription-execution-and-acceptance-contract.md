# 268. Personal subscription execution and its acceptance contract

Date: 2026-11-04
Status: Draft

## Context

Curie's factory has no model credential owner contract. [ADR 0005](0005-claude-agent-sdk-adapter-and-frozen-aci.md)
records the SDK adapter and the need for a production authentication decision.
[ADR 0088](0088-per-user-delegated-oauth-for-mcp.md) concerns delegated MCP
authorization, not model authentication. [ADR 0166](0166-tenant-boundary-and-principal-identity-land-together.md)
provides tenant principals and identity links, but does not bind model billing
authority to an execution. This Draft proposes that binding for #5370; #5371
tracks the decision record. It authorizes no implementation or subscription use.
Acceptance requires explicit maintainer approval under [ADR 0085](0085-acceptance-not-implementation-authorizes-an-adr.md)
and [ADR 0102](0102-accepted-alongside-implementation-with-explicit-approval.md).

The experiments recorded in #5371 are inputs, not product acceptance. Fresh
runner processes completed authenticated turns with a setup token through
`build_options`, `ClaudeAgentSession`, `SessionRunner`, a bundle hook and an
in-process MCP challenge; built-in coding tools were disabled in that probe.
Separate Secrets survived pod recreation. However, a Pod creator could mount
another owner's Secret despite lacking Secret read permission, and deleting a
Secret did not remove its copy from a running pod.

Synthetic sentinels exposed saved `.credentials.json` profiles through native
Read, Bash and hook callbacks, including direct paths, symlinks, hardlinks and
`/proc` root aliases. File permissions and native `filesystem.denyRead` did not
contain every channel. Strict Bash sandboxing failed to start in hardened pods;
masking the whole process also removed the CLI's authentication access. None
of those configurations is evidence of a usable containment boundary.

## Decision

### 1. Explicit mode and native token launch

Prefer a long-lived token generated by the user through the provider's own
unmodified `claude setup-token` browser flow. Curie builds no password or login
collector and mounts no saved native login or refresh profile in a coding
sandbox. The candidate custody shape stores the user-supplied token in a
Kubernetes Secret outside the coding environment and delivers
`CLAUDE_CODE_OAUTH_TOKEN` only to the native CLI through a controlled launch
boundary. This custody shape is conditional on the provider conclusion in
section 5 and the containment result in #5372; it is not an approved design.
#5374 implements only a boundary that passes that experiment. Failure stops
delivery work and requires redesign and a new estimate.

Personal and service authentication are explicit selections. In personal mode,
#5373 must exclude every higher-priority credential source documented below:
cloud provider selectors, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY` and
`apiKeyHelper`, including settings that introduce them. It also removes
`ANTHROPIC_BASE_URL`, `CURIE_MODEL_BASE_URL` and other provider endpoint or
credential overrides, so a grant cannot reach a substituted endpoint. A signed-in
Claude apps gateway session and managed settings that force gateway login also
outrank the ordinary credential list; #5373 must exclude them or refuse launch.
No saved profile or `/login` credential may become a fallback. A missing owner
grant refuses before launch, even with a working service credential present.

The implementer and both factory reviewer roles use the same recorded owner
grant and an explicitly configured Claude reviewer model. Credential shape
cannot select a default reviewer. #5373 owns routing; #5375 proves the complete
single-profile factory path. Service mode retains its existing behavior.
The Kubernetes-only personal pilot refuses personal mode in Docker and skill
tiers, and refuses ownerless runs or evals (#5378).

### 2. Immutable owner and generation

Reuse ADR 0166 `Principal` and `IdentityLink`, with the existing provider identity
namespaces, to resolve the initiating principal. #5376 must persist the tenant,
original owner principal and enrollment generation at admission with versioned
writes and stale-version conflict tests. These are internal API, SQL and claim
facts. This decision changes neither frozen `packages/aci-protocol` nor
`packages/plugin-format`.

The original owner is immutable for the run's lifetime. A different principal
may approve an authorized action, but approvers, CI repair rounds, adoption,
steering, worker recovery and process or pod restarts cannot transfer billing
ownership. #5378 selects grants from the persisted execution owner and validates
tenant, owner and active generation before launch, reuse, adoption, steer or
resume. A wrong owner or tenant, missing enrollment, or stale generation is a
refusal before protected work. Retained routes cannot supply a newer author as
the owner. No new identity namespace or automatic identity linking is implied.

### 3. Enrollment, failure and disconnect

#5377 owns owner-scoped CLI/API enrollment, atomic replacement, reconnect and
disconnect. Enrollment records an active generation. Replacement or reconnect
advances that generation atomically and fences every older runtime and retained
claim; #5378 enforces the fence. The original owner remains fixed. An authorized
resume may bind the new active generation only through an explicit enrollment
revalidation and a fresh process, preserving the workspace and run identity.
There is no in-place credential swap or automatic native-profile refresh.

Do not infer expiry from token text or prefix. A missing token at launch,
a lost grant during an active run, or a rejected or expired token yields an authentication-required result,
stops model progress without service fallback and preserves the owner and
workspace. #5377 implements classification and replacement; #5378 carries them
through repair and recovery.

Disconnect marks the enrollment inactive, invalidates its generation, stops
that owner's runtimes, and blocks later launch, reuse and resume even after a
worker restart (#5377, #5378). Secret deletion alone is insufficient because
live pods retain copies. Disconnect does not revoke the token at the provider
and cannot retract inference already billed. #5379 proves another independently
enrolled owner continues while the disconnected owner's runtime stops.

### 4. Custody and pilot boundary

The installation's trusted worker and anything able to create Pods can read
stored owner grants. Secret read RBAC alone does not contain a Pod creator.
Cluster administrators and the trusted launch components are inside this
custody boundary; the model, bundle hooks, native coding tools, local MCP
servers and helpers are outside it. #5374 must keep token bytes out of their
files, environments and readable process aliases, and out of claims, manifests,
logs, traces, events, API responses and publication artifacts. The storage
Secret is the explicit token-bearing exception, accessible only within the
declared trusted boundary. This is a required future protection, not a claim
about the current runner.

The first pilot has one configured profile, cold claims, no shared owner pool,
and one active process per profile, with sequential reviewer processes (#5375).
It proves use of that configured
grant, not human attribution. #5376 through #5378 introduce owner-aware admission
and lifecycle checks before #5379 qualifies two independent owners. No claim of
tenant isolation exceeds the checks actually implemented and observed.

### 5. Provider eligibility remains unresolved

Retrieved on **2026-11-04** from Anthropic's
[Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)
and [Authentication](https://code.claude.com/docs/en/authentication) pages.
Quoted sentences and excerpts below are verbatim; surrounding interpretation
does not establish provider approval.

The legal page's hosted-product conditions include:

> Unless we’ve mutually agreed otherwise, preinstalling or running Claude Code in your products or services (e.g. in hosted sandboxes or other agent infrastructure) requires agreeing to our Commercial Terms of Service and complying with the conditions below:

> Claude Code must be installed and run as published by Anthropic, and customers may not remove, disable, or restrict any authentication method built into it (including methods that permit signing in with a Claude account or the user’s own API key).

> Customers may not pay for, resell, or intermediate Claude usage on their end users’ behalf.

> Each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential (Amazon Bedrock, Google Cloud’s Agent Platform, Microsoft Foundry).

Its authentication restrictions include:

> OAuth authentication is intended exclusively for purchasers of Claude Free, Pro, Max, Ultra, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications.

> Advertised usage limits for Pro, Max, and Ultra plans assume ordinary, individual usage of Claude Code and the Agent SDK.

These scope and usage-limit statements bear on open question 4: an unattended
factory with reviewers and repair rounds still needs a conclusion about
ordinary, individual subscription use.

> Developers building products or services that interact with Claude’s capabilities, including those using the Agent SDK, should use API key authentication through Claude Console or a supported cloud provider.

> Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, Max, or Ultra plan credentials on behalf of their users.

The same paragraph expressly prohibits the following custody behavior:
“developers may not collect, store, or intermediate Claude.ai credentials or session tokens”.
Sign-in must complete through Anthropic's own flow. The provisioning paragraph
states:

> This does not restrict how customers provision and manage their own API keys or third-party inference provider credentials — for example, configuring an API key in a development environment, secrets manager, or machine image for use by the customer’s own authorized users — provided the resulting usage is billed to the key owner under their agreement with Anthropic (or the applicable provider) and is not resold or intermediated as described above. Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code as described under Can customers offer Claude Code in their products? above.

The secrets manager and machine image carve-out covers API keys and third-party
inference provider credentials, not subscription tokens. Open question 2 must
resolve the proposed subscription-token Secret custody separately; this
paragraph does not grant that permission. Its no-resale and no-intermediation
conditions also bear on open question 4.

The authentication page documents the candidate token mechanism:

> For CI pipelines, scripts, or other environments where interactive browser login isn’t available, generate a one-year OAuth token with claude setup-token:

> It does not save the token anywhere; copy it and set it as the CLAUDE_CODE_OAUTH_TOKEN environment variable wherever you want to authenticate:

> This token authenticates with your Claude subscription and requires a Pro, Max, Ultra, Team, or Enterprise plan.

> It can only make model requests, so it can’t establish Remote Control sessions or fetch claude.ai connectors.

> MCP servers you configure locally still work.

> Bare mode does not read CLAUDE_CODE_OAUTH_TOKEN.

Under “Authentication precedence”, the documented order is cloud provider
credentials selected by `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX` or
`CLAUDE_CODE_USE_FOUNDRY`; `ANTHROPIC_AUTH_TOKEN`; `ANTHROPIC_API_KEY`;
`apiKeyHelper`; `CLAUDE_CODE_OAUTH_TOKEN`; named profile, federation variables,
or an active federation profile; then `/login`. An unnamed profile saved by `ant auth
login` ranks below `/login`. The page separately documents a signed-in Claude
apps gateway session as a provider selection outside this list that outranks
the cloud selectors; forced gateway managed settings can skip the other
sources. Those paths must be excluded or refused, not overlooked by environment
scrubbing. Base URL overrides also require removal for the endpoint guarantee
in section 1. Personal mode cannot use `--bare`.

The text permits an end user to sign into a hosted, unmodified native binary
under the stated Commercial Terms and conditions. Generating a setup token
through the provider flow is documented; neither fact authorizes every way of
embedding or storing it. Curie's runner drives the CLI through
`claude-agent-sdk`, placing it within the explicit SDK/API-key guidance.
Routing factory sessions on behalf of users appears restricted by the
subscription-routing prohibition. The proposed installation Secret stores the
user's token and appears to fall directly within the prohibition on collecting,
storing or intermediating credentials. Keeping the binary unmodified does not
resolve those restrictions, nor the possible conflict between excluding
alternative auth sources and the condition against restricting auth methods.

Before acceptance, a maintainer must resolve and record:

1. Whether the concrete SDK-driven factory is eligible hosted native-binary use
   or prohibited third-party subscription routing, including autonomous repairs
   and reviewer subprocesses; what provider clarification supports that conclusion.
2. Whether customer-controlled installation Secret custody and controlled launch
   are permitted, or require direct end-user authentication with a different
   custody design or an explicit agreement.
3. Whether mode-specific credential scrubbing, helper exclusion and cold launch
   comply with the requirement to leave all built-in authentication methods
   available; how that coexists with deterministic no-fallback execution.
4. Which applicable Commercial Terms, plan eligibility, ordinary individual use
   limits and no-intermediation conditions cover the operator and end user,
   without paying for, reselling or intermediating their usage.

Record the permitted concrete shape and its basis before accepting this ADR
or dispatching dependent implementation. If the candidate is ineligible, revise
this Draft and the tickets rather than implementing a workaround. A successful
test inference proves authentication liveness only; it is never provider approval.

### 6. Acceptance contract

These observable outcomes are future acceptance gates, not results delivered
by this documentation PR. Each numbered row names its proof issue and environment.
Use dedicated test grants delivered privately; captures and public reports
contain no credentials or real deployment identifiers. A row passes only with
recorded candidate commit, exact driver command, expected and observed outcome,
and owned-resource cleanup evidence. Static inspection does not replace a named
runtime check. The #5372 experiment informs this Draft; implementation gates
also require ADR acceptance and a permitting provider conclusion.

1. **Explicit mode and no fallback.** #5373; runner boundary tests and a real
   authenticated CLI turn on a throwaway Kubernetes cluster. Supply conflicting
   cloud selectors, API/auth tokens, helper settings, base URL overrides and
   gateway sessions or forced gateway settings;
   prove only the owner grant authenticates and the expected endpoint is used.
   Remove the grant: authentication-required occurs before a service session
   starts. Service mode remains live. #5378 also proves Docker, skill and
   ownerless personal runs refuse at their actual launch boundaries.
2. **Containment with liveness.** #5372 qualifies the launch design; #5374 proves
   its implementation on a throwaway Kubernetes cluster using the production
   runner and real native CLI. Native Read, Bash, bundle hooks, local MCP and
   helper subprocesses cannot recover a synthetic sentinel placed exactly where
   the real token is delivered, through direct, symlink, hardlink, environment,
   `/proc` environment or root aliases. Each channel reads an ordinary public
   control file successfully, and real inference succeeds in the same
   configuration. Check claims, manifests, logs, traces, events, API responses
   and published output for token absence. A denied operation without its positive control is
   not PASS; a failed #5372 result stops #5374.
3. **Implementer and both reviewers.** #5373 and #5375; real factory admission
   on a throwaway Kubernetes cluster with one dedicated test grant. Drive a
   complete task through the implementer and both reviewers, real ACI tools and
   a bundle hook, and observe all three roles using the owner grant and the
   configured reviewer model without a service credential.
4. **Approval by another principal.** #5376 persists the invariant in
   Postgres-backed API tests; #5375 and #5379 prove it through operator approval
   on a throwaway Kubernetes cluster. Bind an explicit `approvers.users` route,
   approve as a different authorized principal, and observe the original owner
   and grant after resume; an unauthorized principal cannot approve.
5. **CI repair.** #5378 proves worker handling with real Postgres and Valkey;
   #5379 drives a failing fixture CI result and repair through the real factory
   and an owned forge fixture on a throwaway Kubernetes cluster. The repair
   retains its owner and active grant, returns passing CI, and never uses an
   ambient service credential.
6. **Process, pod and worker restart.** #5375 proves pod restart for the
   single-profile pilot; #5378 and #5379 prove the owner-aware recovery paths
   on a throwaway Kubernetes cluster with Postgres, Valkey and durable workspace
   storage. Restart each independently and verify workspace contents, original
   owner and authorized generation in the new process before continued work.
   No assertion depends on the old process retaining a token or workspace.
7. **Wrong-owner steer and adoption.** #5378; worker boundary tests with real
   Postgres and Valkey, plus #5379 on a throwaway Kubernetes cluster. Another
   owner's steer or adoption is denied before tool execution or grant selection;
   the original authorized owner can still continue. Wrong-tenant lookup also
   fails (#5376).
8. **Stale generation.** #5376 tests stale-version conflicts in Postgres;
   #5377 and #5378 exercise replacement, retained claims and recovery on a
   throwaway Kubernetes cluster. After generation advancement, old launches,
   reuse, steer, adoption and resume are denied; an explicitly revalidated fresh
   process with the active generation remains live.
9. **Missing, rejected and expired grants.** #5373 proves missing-at-launch;
   #5377 and #5378 prove missing grant material, rejection or expiry during real factory execution on a
   throwaway Kubernetes cluster, using a dedicated test grant with a provider
   rejection or observed expiry. Each stops as authentication-required without
   fallback and preserves owner and workspace. Token shape or a synthetic error
   alone cannot prove provider expiry behavior.
10. **Replacement and reconnect.** #5377; owner-scoped CLI and API backed by
    Postgres and Secrets on a throwaway Kubernetes cluster. Replace the grant,
    advance the generation atomically, fence the old runtime, and resume only
    in a fresh process after revalidation. Disconnect and reconnect advances
    again. Another principal's enrollment or replacement request is denied.
11. **Disconnect while another owner continues.** #5377 and #5378 implement;
    #5379 proves two independently enrolled dedicated grants on a throwaway
    Kubernetes cluster. Disconnect the first owner during execution, observe
    runtime termination and durable denial after worker restart, and observe
    the second owner's task completing on its own grant. Two owner labels over
    one grant are insufficient. No provider revocation or billing reversal is
    inferred.
12. **Approved publication.** #5375 and #5379; real factory, operator approval
    and an owned forge fixture on a throwaway Kubernetes cluster. Observe no
    publication before approval, then the authorized pushed commit and PR with
    its CI outcome and unchanged execution owner; include a rejected approval
    control. Remove all owned resources and grant copies and verify absence.
13. **Slack issue-link kickoff.** #5380; a real Slack test surface feeding
    production admission on a throwaway Kubernetes cluster. An enrolled sender's
    verified identity resolves to the owner principal, the issue link admits
    work through trusted factory admission, and progress and final status reach
    the originating thread. An unenrolled sender receives a refusal. An API
    substitute or fabricated tracker label event is not Slack proof.

### 7. Scope boundaries

Codex execution is outside this ADR and remains governed by the harness work
in #4440. Slack issue-link kickoff is the feature #5380 and needs no separate
architectural decision here; row 13 records its integration proof, not a new
conversation system. Durable clarification conversations are outside that
feature. No frozen package, chart, or runtime change ships with this Draft.

## Consequences

1. Every claimed protection has an existing source limit or a realizing issue:
   auth and reviewer selection #5373; containment #5372 and #5374; pilot proof
   #5375; immutable ownership #5376; enrollment lifecycle #5377; worker admission
   and recovery enforcement #5378; two-owner proof #5379; Slack integration
   #5380. None becomes implemented through ADR publication.
2. Operators entrusted with Pod creation remain credential custodians. Separate
   Secrets, file modes and Secret read RBAC do not prove owner isolation.
   The complete native-channel matrix and inference liveness must both pass.
3. Cold claims and one active process per profile constrain initial throughput.
   They avoid shared owner pools until ownership and lifecycle fences have proof.
4. Replacement and disconnect require process termination and durable workspace
   recovery, with explicit authentication-required handling instead of silent
   continuation on a different billing identity.
5. Eligibility and containment may invalidate the proposed custody shape.
   This remains Draft until a maintainer resolves those questions and approves
   the decision; successful probes cannot supply that authority.

## Alternatives

1. **Mount saved login or refresh profiles.** Rejected because #5371's synthetic
   probes exposed them through native tools, hooks and path aliases despite file
   permissions; refresh credentials also enlarge custody beyond a model token.
2. **Share one installation subscription.** Rejected because it loses individual
   billing ownership, couples disconnect and concurrency across owners, and
   conflicts with the provider's individual-use and no-intermediation conditions.
3. **Infer ownership from the latest message author.** Rejected because an
   approver, repair or recovery event can author the next turn without becoming
   the original execution owner. Admission must persist the canonical principal.
4. **Silently fall back to a service credential.** Rejected because it spends
   under a different authority and masks missing, rejected or expired enrollment.
5. **Use only RBAC or environment scrubbing as containment proof.** Rejected
   because Pod creation can mount another Secret and filesystem/native-tool
   channels can bypass an environment-only boundary. Require the full matrix.
6. **Build a custom login collector or automatic profile refresh.** Rejected
   because it intermediates provider sign-in and introduces refresh custody.
   Users generate and replace tokens through the provider's own flow.
7. **Adopt API-key execution instead of personal subscriptions.** Remains the
   documented product/SDK authentication route if subscription eligibility or
   containment fails. It does not meet this epic's personal subscription goal;
   it must not be a hidden fallback or be reported as personal acceptance.
